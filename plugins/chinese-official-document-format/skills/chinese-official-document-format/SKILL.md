# 公文格式处理

将内容排成可编辑的 Word 公文，或检查已有公文。格式依据为随技能附带的匿名化规则，来源是用户上传的《公文处理格式要求》；不宣称等同于所有机关的现行统一标准。

## 任务与依据

- 先读取 [格式规则](references/format-rules.md)，确定文件类型与当次要求。普通汇报、报告、通知等未指定红头的材料采用日常公文配置，不增添单位标识。
- 当次用户要求优先；当次明确指定的原生模板优先于通用表。只要求排版时保留原文、顺序、表格数据和附件关系。只有用户同时要求起草、润色时才改写文字。
- 真实单位名称、落款、发文字号、主送机关、日期由本次输入提供。不要使用示例中的名称，也不要因本技能包匿名化而删除用户本次正文中的真实信息。缺少必要信息时明确指出，不编造。
- 函件截图与总表的一级标题字号存在差异，处理方式见规则的“实现约定与冲突”。不把截图当成完整、可编辑的函件模板。

## 制作与修改

1. 识别主标题、一级至五级标题、正文、主送机关、表格、附件说明、附件正文、落款、日期和版记。只有存在实质歧义时询问；不要仅凭字体大小认定段落角色。
2. 标题使用手工编号文本“一、”“（一）”“1.”“（1）”“①”，关闭自动列表。正文及标题的字体、字号、缩进、行距按规则逐项设定，避免 Word 主题色和默认样式覆盖。
3. 普通公文的新建可使用 [DOCX 生成器](scripts/format_docx.py)。先查看 `--help` 和 [结构化输入说明](references/script-usage.md)，把已确定的段落角色写入 UTF-8 JSON。脚本仅生成日常公文；红头、会议纪要及固定函件应使用当次原生模板或直接按规则编排，不能用日常配置代替后宣称已完成。
4. 编辑已有 DOCX 时使用能够保留表格、图片、超链接、域、修订和分节的编辑方式。该生成器不用于导入或覆盖既有文件。输出另存新文件。
5. 红头及会议纪要的首页与后续页采用不同上边距，奇偶页页码和版记按规则处理。不能仅勾选“首页不同”就声称正文页边距不同；通过原生模板或经过分页验证的分节设置实现，不以正文空行冒充红头。

## 交付检查

- 核对文本和表格数据未丢失、顺序未改变；检查自动编号、页边距、字体、字号、字符缩进、段落行距、表头重复及附件数量。
- `scripts/format_docx.py check` 能检查本包生成的日常公文的 XML 属性，也能对其他 DOCX 给出有限诊断；它不计算实际分页，不能代替完整格式验收。详见脚本说明中的覆盖范围。
- 用当前环境的 Documents 工作流或可用的 Word／LibreOffice 渲染器导出并逐页检查。确认字体实际生效，正文无裁切，附件说明和落款日期未独立成页，附件各自另起页，版记确实位于偶数页。未完成渲染时说明“已检查结构，尚未验证分页”，不声称排版验收通过。
- 缺少指定字体时保留正确字体声明，明确告知字体未验证；用户已指定替代字体时直接采用并说明实际偏离，未指定时再询问，不静默换成相近字体。技能不分发字体文件。
- 输出用户要求的 DOCX；只有明确要求或交付方式需要时提供 PDF。说明实际未满足的格式要求，不添加业务内容或多余封面。

## 匿名化范围

本技能本身不保留来源单位、人员、地址、电话、网站、商标、办公系统流程、截图或原始 PPTX。用户另行要求对本次公文匿名化时，再处理本次材料并检查正文、页眉页脚、属性、修订、批注和媒体；未经要求，不对本次业务正文做匿名化。
